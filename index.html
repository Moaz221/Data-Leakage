01 — Concept and Architecture

What Is Data Leakage?

Data leakage is the accidental use of information from outside the legitimate training boundary. The information may come from the future, from the held-out test set, from duplicate observations, or from a variable created after the target event.

Target Leakage

A feature contains information created after, or because of, the target event. The feature may be highly predictive offline but unavailable when the model is actually used.

Typical Example Using a cancellation reason to predict whether an order will be cancelled.

Train–Test Contamination

Information from the held-out test set influences preprocessing, feature selection, hyper-parameter tuning, or model fitting.

Typical Example Computing scaling statistics or selecting features on all rows before splitting.
— The correct order of operations
Raw Data
Split Train / Test
Fit on Train Only
Train Model
Evaluate Test
The test set must remain untouched until the final evaluation. The common mistake is to fit preprocessing on all rows before the split.
02 — Step-by-Step Implementation

The Wrong Way vs. the Safe Way

The example uses 10,000 random features and random binary labels. Because the labels contain no real signal, a leakage-free classifier should perform close to random chance: approximately 0.50 accuracy.

Feature selection before the split 
# Imports
import numpy as np

from sklearn.ensemble import HistGradientBoostingClassifier
from sklearn.feature_selection import SelectKBest
from sklearn.metrics import accuracy_score
from sklearn.model_selection import train_test_split

# Synthetic data with no genuine predictive signal
rng = np.random.RandomState(42)

X = rng.standard_normal((200, 10_000))
y = rng.choice(2, 200)

# WRONG:
# SelectKBest sees all labels before the split.
X_selected = SelectKBest(k=25).fit_transform(X, y)

X_train_bad, X_test_bad, y_train_bad, y_test_bad = train_test_split(
    X_selected,
    y,
    test_size=0.25,
    random_state=42,
    stratify=y,
)

leaky_model = HistGradientBoostingClassifier(random_state=1)
leaky_model.fit(X_train_bad, y_train_bad)

leaky_accuracy = accuracy_score(
    y_test_bad,
    leaky_model.predict(X_test_bad),
)

print(leaky_accuracy)
# A representative run may produce an inflated score such as 0.76.
⚠ Warning: the test labels influenced feature selection before the evaluation boundary was established.
Feature selection inside a Pipeline 
from sklearn.pipeline import make_pipeline

# Split before learning anything from the data
X_train, X_test, y_train, y_test = train_test_split(
    X,
    y,
    test_size=0.25,
    random_state=42,
    stratify=y,
)

# The selector is fitted only on the training portion.
safe_pipeline = make_pipeline(
    SelectKBest(k=25),
    HistGradientBoostingClassifier(random_state=1),
)

safe_pipeline.fit(X_train, y_train)

y_pred = safe_pipeline.predict(X_test)
safe_accuracy = accuracy_score(y_test, y_pred)

print(safe_accuracy)
# A leakage-free result should be close to 0.50.
✓ Safe workflow: the selector learns from X_train and y_train only, then transforms X_test without relearning.

04 — Detection Workflow

How to Investigate Leakage

Leakage detection starts with understanding the data timeline and the evaluation process, not with immediately choosing a more complex algorithm.

01

Build a Timeline

Document when every feature is created and whether it is available at the exact prediction timestamp.

  • Feature creation time
  • Source system
  • Records used by the feature
02

Inspect the Evaluation Code

Search for learned operations that may have been executed before splitting or outside cross-validation.

  • fit and fit_transform
  • Feature selection and normalization
  • Aggregation and hyper-parameter tuning
03

Run Sanity Checks

Compare the model against simple baselines and intentionally random labels.

  • Evaluate on a later time window
  • Remove suspicious columns
  • Compare against a baseline
04

Review Feature Importance

Feature importance is an investigation queue, not proof that a feature is valid.

  • Inspect high-scoring features
  • Check domain meaning
  • Verify timestamp availability
05 — Challenges and Gotchas

Four Ways a Model Can "See the Future"

Select a card to reveal the common failure mode and the recommended solution.

Target Leakage

01

A post-outcome field becomes a predictive feature.

Problem The feature was created after, or because of, the target event. Solution Remove features that are unavailable at prediction time and document the availability timestamp of every column.

Preprocessing Leakage

02

A transformation learns from held-out rows.

Problem Scaling, PCA, feature selection, or imputation is fitted on the full dataset. Solution Place the transformation inside a Pipeline so every fold learns only from its training portion.

Temporal Leakage

03

Training includes observations from the future.

Problem Random splitting allows future observations to appear in the training set. Solution Use TimeSeriesSplit or rolling-origin evaluation with a suitable gap.

Group Leakage

04

The same entity appears in both training and test data.

Problem The model memorizes a customer, patient, user, or image source. Solution Split by entity using GroupKFold, GroupShuffleSplit, or another group-aware strategy.

Cross-Validation Leakage

05

Preprocessing is fitted once before cross-validation.

Problem Every fold has already seen information from its held-out rows. Solution Pass the complete Pipeline to cross-validation instead of passing only the final estimator.

Identifier Leakage

06

An ID encodes identity, chronology, or batch information.

Problem The model learns a pattern that will not transfer to new entities or future batches. Solution Remove identifiers by default or document why they are valid and stable at prediction time.

08 — Results and Next Steps

Build More Credible Evaluations

A lower score is sometimes a better result when it reflects the deployment reality. The objective is not to maximize the validation number at any cost — it is to measure the performance that can be expected on genuinely new data.

What the Experiment Shows

On random labels, a leaky protocol can produce an impressive-looking score even though there is no real predictive signal.

  • Leakage makes weak models look stronger.
  • The evaluation boundary must be protected.
  • Pipeline-based preprocessing is safer.
  • Time and group boundaries must match deployment.

Recommended Next Steps

Add leakage checks to the project definition of done before publishing or deploying.

  • Review every feature timeline.
  • Freeze the final test set.
  • Use time-aware or group-aware splitters.
  • Investigate unexpectedly high metrics.
